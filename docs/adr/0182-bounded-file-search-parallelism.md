# ADR 0182：文件搜索并行度上限

## 状态

已接受（2026-09-20）

## 背景

`files.search` 已经在 Tokio blocking worker 中执行，但目录遍历仍使用
`ignore::WalkBuilder::threads(0)`。该配置会根据机器 CPU 自动创建遍历线程。对
大型目录、慢速磁盘或网络路径进行搜索时，搜索会抢占全部 CPU、磁盘和 blocking
worker，导致 Haven 的 WebView、音频和会话响应看起来整体卡死。

## 决策

将文件搜索的目录遍历线程数固定为 2。搜索仍可并行处理目录项，但不再让机器
CPU 数量直接决定资源消耗；已有的单次搜索 semaphore 和取消 token 继续作为第二层
资源与生命周期约束。

## 替代方案

- 继续使用自动线程数：搜索吞吐更高，但交互式桌面应用没有资源隔离，拒绝。
- 完全改为单线程：响应性最稳，但会不必要地降低本地 SSD 上的搜索吞吐，暂不采用。
- 把搜索移到独立进程：隔离性更强，但超出本次问题范围，后续若需要强制终止原生
  文件系统调用再评估。

## 影响、验证与回滚

不改变文件搜索的输入/输出契约、数据库或配置，不需要用户重置。验证包括
`haven-tools` 文件搜索测试、格式化、严格 Clippy 和 workspace 测试；回滚代码即可。

# Haven 开发与架构治理规范

> 版本：v1.2 | 日期：2026-10-04
> 适用范围：所有 Rust、Svelte、配置、数据库、测试、CI 与文档变更。  
> 项目定位：个人 Windows 助手的测试版本；为正确性、清晰性或安全性可进行破坏性重构。

## 1. 核心原则

1. **规范优先**：先定义不变量、边界与验收，再写实现；不能由“先合并、以后整理”取代。
2. **优雅以清晰为准**：一个概念只有一个权威来源；依赖单向；接口表达意图；失败路径与成功路径同等完整。
3. **允许删除**：测试版不保留没有明确价值和到期日期的兼容层。删除旧数据库、配置、快照或内部 API 时，必须给出重置范围。
4. **小步落地，大边界重构**：可以跨 crate 或跨端重构，但每一步必须可编译、可测试、可回退；禁止一次性改写多个无关域。
5. **风险前置**：涉及文件、进程、系统设置、网络、凭据或模型输出时，先完成威胁分析和负向测试。

## 3. 架构与模块边界

- `haven-common` 只放跨 crate 的稳定数据类型、纯函数和配置模型；不得吸收业务编排或 Tauri/UI 细节。
- provider 协议、重试、流式和媒体实现只在 `haven-llm`；agent、tools、app 不得实现供应商特例。
- `haven-agent` 只编排会话与 ReAct；`haven-tools` 只定义和执行能力；`haven-app-binary` 只装配和适配 Tauri。
- 新增依赖前必须说明为什么不能通过已有下层接口解决；不得引入反向依赖、循环依赖或“临时”跨层调用。
- 任一文件达到约 800 行，或同时拥有超过两个独立职责时，必须在同一任务中说明保留理由或拆分计划。800 行是职责复核触发器，不是拆分目标；审查时区分生产逻辑与同文件测试。拆分必须由稳定 owner/接口支撑，crate 拆分还须证明存在独立依赖边界和实际消费者收益。

## 4. 数据、配置与兼容性

- 数据库 schema、配置 schema、session event 与 Tauri wire payload 都是版本化契约；变化必须有正向与异常路径测试。只有持久数据发生迁移或重置时，才要求对应的迁移/重置测试；若明确不影响持久数据，ADR 必须记明无需重置及其依据。ReAct snapshot 已删除，不得作为持久化或恢复契约重新引入。
- 本版本允许破坏性变化：删除兼容分支前先删除其所有读写入口与测试；在发布说明写明应删除的数据库、配置或缓存路径。
- 禁止双写、双真源和靠内容比对的隐式去重；权威来源必须可从代码与文档中唯一定位。
- 配置默认值必须安全、可解释且经过测试；无法初始化的可选能力应降级并可观测，不能 panic 或静默失效。

## 5. IPC、事件与前端状态

- Tauri 命令请求/响应与事件 payload 优先使用命名 DTO；跨端仅在边界进行 snake_case ↔ camelCase 转换。
- `serde_json::Value` 仅用于 provider 原始载荷、动态工具参数或明确的扩展点；不得作为稳定业务接口的默认选择。
- 每个事件必须定义生产者、消费者、顺序/幂等要求、敏感字段和测试；事件映射只能有一个登记点。
- 路由页负责加载与编排，视图/组件负责展示和局部交互；禁止把业务状态机、事件订阅和大段渲染继续堆入单一 Svelte 文件。

## 6. 安全与 Windows 边界

- 所有文件写入、进程启动、注册表、电源、环境变量和外链打开都必须经过同一安全网关与风险分级；前端不得成为绕过路径。
- `unsafe` 和 Windows FFI 必须保持在最小适配模块，说明安全前提，并对失败、句柄、字符串、线程初始化和权限拒绝写测试。
- 路径校验必须覆盖规范化、重解析点/符号链接、源与目标路径、相对路径、UNC、取消与竞态。
- 渲染模型文本时坚持默认拒绝 HTML、最小化外链能力、设置明确 CSP；安全降级应有用户可见反馈和日志。
- 密钥、令牌、隐私内容和完整命令输出不得进入 UI 错误文案、普通日志或测试 fixture。

## 7. 测试、质量与性能

- 单元测试使用临时目录/内存数据库/显式注入的依赖；不得读写真实用户目录、系统配置、网络或全局环境，除非测试名称明确且被隔离。
- 所有 bug 修复先增加会失败的回归测试；所有重构保持行为测试，除非该行为被明确删除。
- 门禁按变更影响面选择，最低范围如下：
  - Rust 单 crate 内部切片：格式化，以及受影响 crate 的 locked 编译、严格 Clippy 和相关测试；涉及跨 crate 公共契约、共享存储或持久化恢复时升级为 workspace 门禁。
  - UI 切片：运行前端检查与测试；改动构建配置、路由装配或生产资源时增加生产构建。
  - Rust↔UI IPC/事件切片：Rust workspace 编译、严格 Clippy 与测试，前端检查、测试与生产构建，以及适用的 IPC 生成/漂移检查。
  - 数据、配置、安全或 Windows 系统边界切片：覆盖失败、拒绝、重启/恢复与适用的重置语义；依赖真实 Windows 行为的最终验收在 Windows 环境完成。
  纯文档切片按 Git 流程做格式、链接和差异检查。覆盖率只作为趋势，阈值一旦设定即为阻断门禁。
- 新增缓存、后台任务、流式处理或大文件路径时，必须给出容量上限、取消行为、并发模型与至少一个压力/边界测试。
- CI 需固定工具链并覆盖 Windows；依赖升级、安全扫描和构建产物检查属于定期维护，不依赖人工记忆。

## 8. 文档、ADR 与变更管理

- 新功能、删改契约、跨 crate 改动、安全语义、数据库变更必须附简短 ADR：背景、决定、替代方案、影响、验证与回滚/重置。
- README 应覆盖项目用途、开发环境、启动、测试、数据重置、故障报告和发布；`AGENTS.md` 不替代面向开发者的入口文档。
- 提交采用 `feat`、`fix`、`refactor`、`docs`、`test`、`build`、`chore` 前缀；每次提交只表达一个可审查目的。
- 模型可见工具目录、按需加载和 operation 命名遵循 [架构文档](architecture.md) 及 ADR 0140–0148、0198；不要在本规范复制工具目录实现细节。工具名、权限 key、配置、UI renderer 和历史配置迁移必须共享正式名称。删除或重命名入口时，同时删除无调用的 UI/测试分支，并为旧配置定义一次性迁移或明确重置边界。
- Git 的分支、暂存、验证和提交节奏遵循 [Git 提交流程](git-workflow.md)；每轮逻辑改动完成且适用门禁通过后应主动提交。
- 合并前的定义完成（DoD）：代码、测试、相关规范/ADR、风险评估、验收命令与用户可见变更说明均已更新。

## 9. 重构执行模板

1. 写出要删除的旧设计、目标不变量、影响面和验收测试。
2. 建立目标接口与测试夹具，迁移一个完整调用链。
3. 删除旧实现、旧配置、旧测试和旧文档入口，禁止保留无调用的“备用”代码。
4. 按第 7 节的影响面门禁矩阵验证；跨 crate/跨端、持久化或安全边界切片跑相应全量门禁。只在架构边界或契约实际变化时更新架构图、ADR 与重置说明，并在 ADR 中记录未执行或受环境限制的验收。
5. 大范围重构按领域独立提交；Git 历史重置仅在稳定版本验收后单独执行。

## 10. 当前架构状态

阶段状态和待办会随实现变化，集中维护在[架构重构路线图](architecture-refactor-roadmap.md)；本规范只保留长期有效的工程规则。
